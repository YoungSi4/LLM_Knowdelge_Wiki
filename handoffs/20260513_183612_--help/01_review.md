# 🔍 Design Review

이전 단계를 엄격한 리뷰어(Reviewer)의 시각에서 검토한 결과, **치명적인 요구사항 오해와 구조적 결함**이 다수 발견되었습니다. 사용자는 `--help` 기능에 대한 **'아키텍처 및 구현 전략(Plan)'**을 요구했으나, 이전 단계에서는 단순히 정적 텍스트로 된 매뉴얼을 출력하는 수준에 그쳤습니다. 

다음은 반드시 재설계되고 수정되어야 할 비판적 결함 및 누락된 엣지 케이스 목록입니다.

---

### 🚨 1. 근본적인 요구사항 불일치 (Missed Core Objective)
*   **설계 문서(Plan) 부재:** 구현을 위한 구체적인 전략, 수정해야 할 파일 목록, 아키텍처 다이어그램, 테스트 시나리오가 포함된 Markdown(`.md`) 형식의 계획서가 전혀 작성되지 않았습니다.
*   **단순 텍스트 출력의 한계:** "어떻게(How) 구현할 것인가"에 대한 답변이 아닌 "이 시스템은 무엇인가(What)"를 답변했습니다. 이는 시스템 분석 및 설계라는 본연의 목적을 완전히 벗어난 행동입니다.

### 🏗️ 2. 아키텍처 및 구조적 결함 (Structural Flaws)
*   **`argparse` 통합 전략 누락:** `orchestrator_full_pipeline.py` 등 기존 스크립트에는 이미 Python의 내장 `argparse`가 적용되어 있어 기본 `--help` 동작이 존재합니다. 기존 `help`를 오버라이딩(Custom Help Formatter)할 것인지, 파이프라인 상단에서 특정 조건을 가로채어 커스텀 도움말을 출력할 것인지에 대한 설계적 판단이 없습니다.
*   **확장성 부재(Hardcoding Risk):** 에이전트 정보나 사용법이 코드나 출력에 하드코딩될 위험이 높습니다. `pool/*.json` 형태의 에이전트 설정 파일이나 환경 변수를 동적으로 파싱하여 최신 상태의 `--help`를 구성하는 동적 로직 설계가 필요합니다.

### ⚠️ 3. 누락된 엣지 케이스 (Missing Edge Cases)
*   **명령어 조합 충돌 (Flag Combinations):** `--help`와 다른 인수(예: `python orchestrator.py "요구사항" --help`)가 동시에 주어졌을 때의 처리 우선순위가 정의되지 않았습니다. (도움말 출력 후 즉시 종료할 것인지, 에러를 반환할 것인지 등)
*   **대화형 모드(Interactive Mode) 예외 처리:** CLI 인자로 `--help`를 넘기지 않고, 대화형 프롬프트 대기열 안에서 사용자가 `help`나 `--help`를 입력했을 때 시스템이 어떻게 반응할지에 대한 방어 로직이 없습니다.
*   **하위 헬프(Sub-command Help):** 특정 에이전트나 모드에 대한 상세 도움말(예: `--help planner`, `--help modes`) 처리를 어떻게 라우팅할 것인지에 대한 설계가 빠져 있습니다.

### 🔒 4. 보안 및 유지보수 취약점 (Security & Maintainability Risks)
*   **내부 동작(Internals) 노출 위험:** 일반 사용자가 `--help`를 입력했을 때, `--approval-mode yolo`나 `system_prompt`의 로컬 절대 경로(`D:\system_analysis\...`)와 같은 내부 인프라 정보가 그대로 노출되는 것은 보안상/사용성 측면에서 부적절합니다. **사용자용(Public) 도움말과 개발자용(Debug/Internal) 도움말 계층 분리** 설계가 누락되었습니다.
*   **Short-circuiting 누락:** `--help` 요청 시 시스템은 무거운 초기화(LLM API 클라이언트 로드 등)를 수행하지 않고 즉시 도움말을 출력한 뒤 빠져나와야(Exit Code 0) 합니다. 초기화 과정 중 불필요한 토큰이나 리소스 낭비가 발생하지 않도록 Entry Point 최상단에서 실행 흐름을 차단하는 설계가 명시되어야 합니다.
