# 의사결정 라운드 및 프로젝트 진행 기록 (Journal)

## 2026-06-12: 아키텍처 안정성 확보 및 2번 과제 목표 설정

### 1. 이전 단계 요약: Conductor 패턴 도입 및 시스템 안정성 확보
- **이슈:** 지식 위키를 업데이트하는 에이전트(Planner, Writer)와 사용자 질의응답을 담당하는 에이전트(QA)의 역할을 명확히 분리하고, 메인 에이전트의 단독 처리를 방지해야 함.
- **의사 결정:**
  - Main Agent를 **Conductor**로 활용하는 Router/Supervisor 패턴 채택 및 명세서(`WIKI_PIPELINE_SPEC.md`) 업데이트.
  - 서브 에이전트 실패 시 위키 오염을 방지하기 위해 **Atomic File Write (임시 `.tmp.md` 파일 후 덮어쓰기)** 방식 도입.
  - 에이전트 실패 시 Conductor가 바로 인지할 수 있도록 표준 출력에 `[ERROR_SIGNAL]` 강제.
  - 각 에이전트별 엄격한 권한 분리 (QA는 읽기 전용, Writer는 쓰기 전용 등).

### 2. 2번 과제 목표 수립: MCP 서버 기반 Wiki Tool
- **이슈:** MCP 서버 기반의 Wiki Tool 구현 및 시각화를 위한 산출물 5종(도메인, Journal, PRD, README, MVP 이미지) 준비.
- **의사 결정:**
  - **지식 도메인 구체화 및 지침화:** 게임 개발 및 데이터 지향 설계(DOD)로 확정. 이 정의서는 단순히 과제 제출용이 아니라 전체 시스템을 관통하는 핵심 지침서로 활용하기 위해 프로젝트 최상위 경로의 `WIKI_DOMAIN_SPEC.md`로 이동 및 승격시킴.
  - **시각화 방식 확정:** 파이썬(현재 백엔드)과 완벽하게 호환되며, 가장 구현이 빠르고 안정적인 **Streamlit(스트림릿)**을 채택하기로 함. (왼쪽 위키 뷰어 + 오른쪽 챗봇 패널 MVP 구상)
  - **MCP Tool 기능 확정:** 읽기 전용이 아닌 **쓰기 기능(`update_page`, `create_page`)을 포함하여 확장**하기로 결정. 쓰기 작업은 Conductor가 아닌 Sub-agent(Writer)를 통해 수행되며, 할루시네이션 방지를 위해 단순 승인이 아닌 **사전 보고(Draft Preview)** 절차를 도입하기로 함 (Planner가 작성한 초안을 먼저 사용자에게 보여주고 확인받은 후 Writer 가동).
  - **기존 아키텍처 통합 확정:** 이전 단계에서 구축한 'Conductor-SubAgent(Planner, Writer, QA) 파이프라인'과 원자성 보장 로직을 이번 MCP 서버 과제의 핵심 기반 아키텍처로 완전히 통합하여 스토리를 이어가기로 결정함.
